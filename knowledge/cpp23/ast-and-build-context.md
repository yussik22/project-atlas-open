# AST не дорівнює успішній компіляції

Clang може повернути часткову translation unit разом із діагностикою
помилок. Отже, `translation_unit != nullptr` означає лише, що дерево вдалося
створити; **не** означає, що файл компілюється без помилок. Atlas зберігає
окремо `parsed`, кількість Clang errors і warnings. Негативний тест із
навмисно зламаним `.cpp` перевіряє саме цю відмінність.

[Специфікація Clang compilation database](https://clang.llvm.org/docs/JSONCompilationDatabase.html)
встановлює, що відносні шляхи в команді інтерпретуються від її `directory`.
Atlas нормалізує підтримувані include/forced-include шляхи відносно цього
каталогу. Він не змінює process-wide current directory під час фонового
сканування: така зміна вплинула б і на GUI-потік. Поки що Atlas переносить
не всі специфічні прапорці компілятора та бере першу команду для файлу,
якщо база має кілька конфігурацій.

[Посібник libclang](https://clang.llvm.org/docs/LibClang.html) описує AST,
translation units та фізичні source locations. Для навігації це потужне
джерело фактів, але його публічний C API не відкриває всіх деталей C++ AST.
Тому кожна автоматична картка Atlas має посилатися на вихідний файл і
показувати діагностику; вона не повинна проголошувати поведінковий контракт.

Практичне правило: **спочатку відтворити конфігурацію збірки**, тоді
інтерпретувати AST, потім перевірити твердження тестом. Коли build context
неповний, класифікувати висновок як неповний, а не як факт про весь проєкт.
