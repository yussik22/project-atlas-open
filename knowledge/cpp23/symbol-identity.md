# Тотожність класу ≠ його хеш

## Питання

Як показувати `alpha::Node` і `beta::Node` окремо та зводити повторні
оголошення **того самого** класу з різних translation units до одного вузла?

## Що гарантує C++23

- `type_info::hash_code()` дає однакове значення для рівних `type_info`
  **в межах одного запуску**; саме значення не визначене. Тому це не
  стійкий ключ для файлу або індексу коду. Див. N4950 §[type.info];
  [текст розділу](https://eel.is/c++draft/type.info).
- `std::type_index::hash_code()` просто повертає хеш вкладеного
  `type_info`; додаткової міжзапускової гарантії немає. Див. N4950
  §[type.index]; [текст розділу](https://eel.is/c++draft/type.index).
- Назва типу, одержана з `type_info::name()`, залежить від реалізації.
  Повне текстове ім'я класу корисне для людини, але не є надійним ключем
  злиття всіх C++-сутностей. `std::source_location` описує місце виклику,
  а не семантичну тотожність оголошення.

Ці висновки не означають, що хеші «погані»: `std::hash` доречний для
контейнерів у процесі. Вони означають, що стандартна бібліотека не надає
готовий персистентний ID для кожного оголошення класу у вихідному коді.

## Що дає Clang

[libclang `clang_getCursorUSR`](https://clang.llvm.org/doxygen/group__CINDEX__CURSOR__XREF.html)
повертає USR — рядок для зіставлення тієї самої сутності між translation
units. Це ключ Atlas для злиття вузлів. `qualified_name` — підпис для
людини, складений із семантичних батьків. USR слід трактувати як opaque:
не розбирати його структуру й не вважати API Clang частиною ISO C++.
Відмінності в прапорцях компіляції та поведінка нових версій Clang можуть
впливати на побудований AST; [документація libclang](https://clang.llvm.org/docs/LibClang.html)
не обіцяє абсолютно незмінну поведінку між версіями.

## Рішення Atlas

| Поле | Роль | Можна використовувати як головний ключ? |
| --- | --- | --- |
| Clang USR | Тотожність AST-сутності між TU | Так, у межах узгодженого індексу/версії |
| `qualified_name` | Читабельний підпис і пошук | Ні; випадки локальних/анонімних сутностей складніші |
| FNV-1a 64 від USR | Короткий Mermaid ID | Ні; можливі колізії |
| Шлях і рядок | Навігація до вихідного коду | Ні; змінюються після редагування |
| `typeid(T).hash_code()` | Runtime type lookup | Ні, для збереженого індексу |

`src/scan.cpp` зберігає USR та кваліфіковане ім'я. `src/report.cpp`
групує за **повним USR**, обчислює короткий ID лише для синтаксису Mermaid
й перед записом схеми перевіряє колізії. Детермінований FNV-1a реалізовано
у `include/atlas/symbol_identity.hpp`; це власний формат Atlas, **не**
стандартний `std::hash`. Якщо USR порожній, зараз є резервний ключ за
кваліфікованим ім'ям; його точність нижча, тож це явне обмеження.

## Перевірка та обмеження

- Тест має довести, що `alpha::Node` і `beta::Node` не зливаються.
- Тест має довести, що помилковий файл має діагностику навіть якщо Clang
  повернув часткове AST; інакше індекс може виглядати повним помилково.
- Колізія 64-бітного хешу не доводить тотожність: при ній генерація схеми
  зупиняється замість тихого об'єднання класів.
- Індекс класів наразі не є повним індексом C++: macros, умовна
  компіляція, шаблонні спеціалізації та відсутні compile flags можуть
  змінити набір видимих декларацій. Для рефакторингу потрібні окремі
  перевірки, а не лише ця схема.
