# Пам'ять: окремо storage, lifetime, ownership і синхронізація

Ця картка потрібна для майбутньої карти логіки пам'яті. Вона не стверджує,
що Atlas уже вміє автоматично доводити коректність роботи з пам'яттю.

## Чотири різні питання

| Питання | Що саме перевіряти |
| --- | --- |
| Storage | Чи отримано достатньо байтів із потрібним вирівнюванням? |
| Lifetime | Чи існує об'єкт потрібного типу в цьому storage саме зараз? |
| Ownership | Хто й коли викликає звільнення або deleter? |
| Concurrency | Чи є happens-before між конфліктними доступами? |

За C++23 §[basic.life] lifetime об'єкта починається лише за належних умов
storage та ініціалізації; звільнення або повторне використання storage може
його завершити. Отже, «адреса ще існує» **не** доводить, що до об'єкта можна
звертатися. [Текст §[basic.life]](https://eel.is/c++draft/basic.life).

`std::unique_ptr` моделює передавання одноосібного володіння, а його
деструктор викликає deleter для ненульового покажчика. Це допомагає
побудувати контракт звільнення, але не доводить правильність часу життя
всіх позичених посилань. Див. C++23 §[unique.ptr.single] і
[деструктор](https://eel.is/c++draft/unique.ptr.single.dtor).

Конфліктні несинхронізовані доступи з різних потоків, якщо хоча б один
неатомарний, можуть утворити data race з undefined behavior; див. C++23
§[intro.races], [текст розділу](https://eel.is/c++draft/intro.races).

## Формат майбутнього тесту Atlas

`expected`: власник, розмір, стан lifetime, допустимі потоки та події
`allocate → construct → borrow → release/destroy`.

`actual`: події, отримані від тестового інструментування, із часовими
мітками/порядком та ID конкретного об'єкта. Порівнювати треба **першу
розбіжність**, а не лише кінцеві значення; однакова кінцева кількість байтів
не виключає use-after-free або гонку.

Статичний AST показує декларації та деякі шляхи коду, але сам по собі не
відновлює всі runtime lifetime-події. Динамічні твердження потребують
вимірювання тестом/санітайзером/дебагером і мають бути позначені як такі.
